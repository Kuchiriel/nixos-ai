- não transforme hipótese em fato.

Nenhum ganho de performance deve ser declarado sem medição reproduzível.

8. NÃO CONFUNDA COMPONENTES

Este projeto possui múltiplos agentes/modelos e ferramentas.

Mantenha explicitamente separados:

- Mimo 2.5 / Freebuff;
- CLI;
- Aider;
- modelo local;
- llama.cpp;
- Roo Dev;
- VSCodium;
- ferramentas MCP;
- infraestrutura NixOS.

Não atribua comportamento de um componente a outro sem evidência.

9. NÃO QUEBRE O AMBIENTE DE EXECUÇÃO

Nunca reinicie, substitua ou interrompa deliberadamente componentes necessários para o próprio agente continuar trabalhando, salvo se isso fizer parte explícita da tarefa e existir uma estratégia segura de recuperação.

Especialmente:

- não reinicie llama.cpp sem necessidade;
- não substitua o próprio agente em execução;
- não altere arbitrariamente configurações de VM/hypervisor;
- não destrua serviços ou arquivos necessários para a sessão atual.

Se uma alteração exigir restart/reload, documente isso antes e determine se existe uma estratégia de validação sem interromper a sessão.

10. NIXOS

Mantenha a filosofia declarativa.

Priorize:

- Flakes;
- módulos Nix;
- Home Manager;
- opções declarativas;
- packages/overlays;
- systemd declarativo.

Não faça configuração manual persistente em ~/.config para resolver problemas que deveriam estar no código declarativo.

Não introduza caminhos absolutos específicos da máquina sem justificativa.

11. SEGURANÇA CONTRA LOOPS DE EVAL

O projeto já sofreu um problema grave de avaliação recursiva/lazy evaluation que consumiu toda a RAM durante build.

Portanto, qualquer alteração em:

- módulos;
- imports;
- mkIf;
- mkMerge;
- mkForce;
- overlays;
- specialArgs;
- module arguments;
- pkgs;
- Home Manager;
- Stylix;
- opções recursivas;
- listas/attrs derivados;

deve ser analisada especificamente quanto ao risco de dependência circular e fixpoint recursivo.

Valide com nix eval/build antes de declarar concluído.

12. NÃO FAÇA FAKE COMPLETION

É proibido considerar uma tarefa concluída apenas porque:

- o arquivo foi criado;
- pytest passou;
- o código compila;
- uma função isolada funciona;
- um mock funciona;
- um benchmark foi executado uma única vez;
- a documentação foi atualizada.

"Implemented" e "Verified" são estados diferentes.

Uma tarefa só vira VERIFIED quando a evidência corresponde ao comportamento que a tarefa realmente exige.

13. QUANDO ENCONTRAR UM PROBLEMA, NÃO CONTORNE SEM INVESTIGAR

Se um teste falhar:

- investigue a causa raiz;
- consulte logs;
- leia o código relevante;
- pesquise upstream quando necessário;
- corrija a causa;
- execute novamente.

Não esconda falhas com:

- timeout maior;
- retry infinito;
- suppress de erro;
- mocks;
- skip de teste;
- flags que mascaram o problema;
- alterações cosméticas.

Se precisar de workaround, documente explicitamente.

14. DÉBITO TÉCNICO

Antes de finalizar cada tarefa, procure:

- código morto;
- duplicação;
- TODO criado pela implementação;
- imports desnecessários;
- arquivos temporários;
- scripts descartáveis que deveriam ser integrados;
- documentação divergente;
- interfaces incompletas;
- tratamento de erro ausente;
- caminhos hardcoded;
- hacks.

Não deixe lixo para trás.

15. DOCUMENTAÇÃO

Depois de qualquer alteração arquitetural ou comportamental:

- atualize a documentação afetada;
- atualize benchmarks;
- atualize HANDOFF quando necessário;
- marque informações antigas como superseded em vez de simplesmente apagá-las quando isso for importante para rastreabilidade.

A documentação final deve refletir o código realmente existente.

16. GIT

Faça commits lógicos.

Antes de cada commit:

- git diff;
- git status;
- testes relevantes;
- verificar arquivos inesperados.

Nunca inclua arquivos pessoais, segredos, credenciais ou artefatos de build.

17. AUTONOMIA

Você possui autorização para:

- ler a codebase;
- pesquisar;
- criar/modificar arquivos necessários;
- executar testes;
- executar builds;
- executar benchmarks;
- refatorar;
- corrigir problemas encontrados;
- atualizar documentação;
- criar commits.

Não pare depois de encontrar a primeira solução plausível.

Continue investigando até atingir o critério de conclusão definido para a tarefa.

18. PRIORIZAÇÃO

Quando existirem muitas tarefas:

P0 = correção, segurança, build, boot, integridade
P1 = funcionalidades quebradas/incompletas
P2 = integração e qualidade
P3 = performance mensurável
P4 = limpeza/refatoração
P5 = melhorias cosméticas

Não gaste a sessão inteira em otimizações cosméticas enquanto houver problemas funcionais ou integração incompleta.

19. REGRA DE "UMA COISA POR VEZ"

"Uma tarefa por vez" NÃO significa "uma pequena alteração por vez".

Uma tarefa deve ser entregue COMPLETA.

Exemplo:

ERRADO:
- criar função;
- pytest passa;
- marcar done.

CORRETO:
- entender requisito;
- pesquisar;
- implementar;
- integrar;
- testar caminho normal;
- testar falhas;
- testar integração;
- testar E2E quando aplicável;
- medir quando aplicável;
- documentar;
- revisar diff;
- corrigir débito técnico;
- commit;
- marcar VERIFIED.

20. PRIMEIRA FASE — NÃO IMPLEMENTE

Sua primeira resposta após ler a conversa e o repositório deve ser SOMENTE uma auditoria.

Entregue:

A. Estado atual real da codebase.

B. Arquitetura atual inferida do código.

C. Diferenças entre documentação e código.

D. Problemas encontrados.

E. Funcionalidades incompletas.

F. Débito técnico relevante.

G. Lista de tarefas priorizada.

H. Critério de validação de cada tarefa.

I. Dependências entre tarefas.

J. Quais itens históricos da conversa já foram resolvidos, quais continuam válidos e quais foram superseded.

NÃO faça alterações nesta primeira fase.

Depois da auditoria, aguarde a confirmação para iniciar a execução do TODO.

REGRA FINAL

Prefira uma implementação menor, correta, integrada e verificável a uma implementação grande, superficial e cheia de débito técnico.

Não me entregue a aparência de progresso.

Entregue evidência de progresso.
Um detalhe importante

Eu não deixaria o link da conversa como única fonte. O ideal é:

conversa → contexto histórico
repo → estado atual
testes/benchmarks → evidência

Isso evita um problema comum de agentes: eles leem uma conversa antiga, assumem que determinada coisa ainda existe, e começam a “corrigir” problemas que já foram resolvidos ou reintroduzem arquitetura antiga.

E, considerando o histórico do projeto, eu manteria a regra mais importante do prompt:

"Uma tarefa por vez não significa uma alteração pequena por vez. A tarefa só termina quando estiver integrada, testada e documentada."

Essa é justamente a diferença entre o Mimo produzir uma sequência de patches que parecem progresso e efetivamente fechar os itens do projeto.
