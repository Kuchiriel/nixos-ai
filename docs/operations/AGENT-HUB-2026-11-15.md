## O que é

Um serviço HTTP (Node puro, zero dependências) que agrega a frota num lugar só:

| Rota | O quê |
|---|---|
| `GET /` | página (cards dos agentes, transcript, conversa do bus, criar agente, estado da casa) |
| `GET /api/agents` | roster + busy/updated (via API do opencode) |
| `GET /api/bus?limit=N` | **a conversa da frota** (bus issue #12, via API do GitHub) |
| `GET /api/models` | catálogo REAL de modelos + medidor de rate-limit |
| `GET /api/state` | estado consolidado: agentes, claims, fila, kanban, spawns, serviços, modelos |
| `GET /api/transcript?session=S` | últimas mensagens de uma sessão (**exige token**) |
| `POST /api/wake` | acorda um agente por nome+texto (**exige token**) |
| `POST /api/spawn` | **cria um agente novo** (modelo, persona MBTI, system prompt) — assíncrono |

Unidade: `agent-hub.service` (user). Fonte: `scripts/agent-hub.mjs`.
Docs do painel: `~/docs/agentes/mission-control-15-11.md` (celular).

## Três coisas que o node deste unit NÃO pode fazer (medido)

1. **executar binário do nix store** — `gh`, `python3` morrem com SIGTERM imediato
   no `spawnSync` (até o `.gh-wrapped`). Por isso: bus lido por **fetch** na API do
   GitHub, e o resto delegado ao Python da casa.
2. **ler o DB do opencode** — o `part`/`message` é o schema 1.x CONGELADO (09/11);
   o 2.2.6 grava em `session_message` (conteúdo dentro do `data`).
3. **decidir "agente vivo"** — não há janela Hyprland num serviço headless; quem
   decide é a API do opencode (`/api/session`) e o `session_input`.

## Criar agente (Grok Bot style)

`scripts/agent-spawn.py`:
1. classifica a tarefa (`team.classify`) → tipo, MBTI, persona;
2. escolhe o modelo (`team.model_for_task` + candidatos ordenados por **força real**:
   ctx do catálogo + tier; local por último);
3. monta o **system prompt** inicial (persona + MBTI + regras da casa);
4. cria a sessão (`opencode run -s <id> -m <modelo> "<tarefa>"`);
5. registra no roster (`~/projects/.agents/roster.json` — o `agent-roster.py claim`
   exige estar numa janela de agente, então o spawn escreve a entrada direto);
6. grava o estado em `~/.local/state/jarvis/spawns/<ses>.json` (a UI acompanha).

**Perfil redteam**: MBTI **INTP** + API primeiro (Nemotron 550B ctx 1.048.576 free →
minimax M3.1 → gpt-oss-120b) e o local Qwen 4B MTP como opção BAR.

**Modelo local e ctx**: o 4B MTP tem ctx 12.288 e o payload do opencode dá 56.147
tokens → só responde com perfil slim (`scripts/spawn-slim.json` +
`OPENCODE_DISABLE_PROJECT_CONFIG=1` + cwd sem AGENTS.md). O Qwen MoE 35B (:8084)
está morto.

## Dedup (o que NÃO pode existir duas vezes)

- **Injeção de prompt**: só `jarvis.core.comms.deliver` (bus + API). O hub usa
  `scripts/deliver.py` → mesmo caminho do `/to` do Telegram e do plugin
  `agent-wake`. Não existe POST próprio do hub.
- **Leitura do bus**: só `/api/bus` (fetch na API do GitHub, cache 90s). O
  `hub-state.py` NÃO relê o bus (custava ~20s e era dup).
- **Catálogo de modelos**: `scripts/model-catalog.py` agrega o catálogo da casa
  (`free-providers.json`) + registry (`models.nix`) + contadores do nv-gate.
  Listas de modelo NÃO são fixas: vêm do catálogo.
